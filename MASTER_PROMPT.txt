## 5. DATABASE — SUPABASE (Postgres)

*(unchanged from your draft)*

Use Supabase (Postgres + built-in auth, even though auth is unused for now —
wire a single default user so switching to real multi-user auth later is a
config change, not a rewrite). Tables:

- **campaigns**: id, name, status (draft/active/paused/completed), icp_filters (jsonb), created_at, org_id (nullable, unused)
- **contacts**: id, campaign_id (fk), graph8_contact_id, name, email, title, company, intent_score, current_step, status (enum: new/enrolled/replied/bounced/meeting_booked), enriched_data (jsonb), created_at
- **variants**: id, campaign_id (fk), channel (enum: email — extendable later), subject, body_template, status (active/killed/draft), sends_count, opens_count, replies_count, positive_replies_count, meetings_count, created_at, killed_at
- **events**: id, contact_id (fk), variant_id (fk), event_type (sent/opened/replied/bounced/meeting_booked), raw_payload (jsonb), sentiment (nullable enum: positive/neutral/negative), created_at — populated by the webhook receiver, this is the feedback loop's raw fuel
- **agent_decisions**: id, campaign_id (fk), decision_type (reallocate/kill_variant/generate_variant/escalate_voice), reasoning (text), before_state (jsonb), after_state (jsonb), requires_approval (bool), created_at
- **approvals**: id, decision_id (fk, nullable), type (send_new_variant/kill_variant/voice_escalation/reply_draft), payload (jsonb), status (pending/approved/rejected), created_at, resolved_at
- **reference_emails**: id, subject, body, style_notes (text, optional), created_at
- **settings**: key (text, pk), value (text) — non-secret UI-visible config only. Real API keys stay in `.env`.
- **mailbox_status** *(new — see Section 6c)*: id, provider (gmail/outlook/smtp), graph8_mailbox_id, connected_at, status (active/warming_up/error) — mirrors what graph8 reports about the connected mailbox, purely for the Settings page to display; graph8 owns the actual credentials, we never store them.

## 6. graph8 INTEGRATION — ADAPTER PATTERN (CORRECTED, VERIFIED ENDPOINTS)

Build `backend/app/adapters/graph8_client.py` as a single class,
`Graph8Client`, exactly as your draft specified — one method per operation,
HTTP details never scattered into business logic. The difference from your
draft: these endpoints are now confirmed against graph8's public developer
docs (`docs.graph8.com/developers/`) rather than assumed, so Antigravity can
build directly instead of guessing.

**Base URL:** `https://be.graph8.com/api/v1`
**Auth:** `Authorization: Bearer <GRAPH8_API_KEY>` header on every request.
An `X-Org-Id` header exists for cross-org service tokens but is not needed
for a normal single-org API key — the org is resolved from the key itself.
**Interactive Swagger** (needs a logged-in graph8 account to view):
`https://be.graph8.com/api/v1/docs` — Antigravity should treat this as the
source of truth if any method below throws a 404/422 during build; a couple
of request-body field names are marked "verify" below because the public
doc excerpts didn't spell out every field.


### 6c. EMAIL / GMAIL — USE graph8's NATIVE MAILBOX CONNECTOR, NOT A CUSTOM ONE (NEW SECTION, REPLACES THE "user enters Gmail creds → n8n connects" IDEA)

**Short answer to "is this possible": the idea as described (user types
their Gmail credentials into our frontend, our backend/n8n uses them to
connect to Gmail) is not something to build — Gmail does not accept
username/password login for third-party apps at all, only OAuth consent.
Any form asking for a Gmail password would be asking users to hand over
their actual Google account password to a hackathon app, which Google's
own policies block and which is a real security problem regardless.**

The good news: graph8 already solved exactly this, natively, with OAuth:

1. **Connecting the mailbox** (confirmed: `docs.graph8.com/settings/mailboxes`)
   happens entirely inside graph8's own UI: Settings → Mailboxes → Connect
   Mailbox → Gmail → the user signs into Google and clicks Allow → done.
   graph8 handles the OAuth flow, token storage, sending-limit detection,
   and optional warmup entirely on its side. **We never see or store a
   password or an OAuth token.**
2. **Our app's job** is just to point the user at that flow and then read
   the result:
   - On our **Settings page**, show a "Connect your inbox" card. Since
     graph8 doesn't expose a way to embed their OAuth flow inside a
     third-party app's own UI (no public "connect-link" endpoint was found
     in the docs, unlike some competitors), the honest, buildable version
     for a hackathon is: a button that says "Open graph8 Mailbox Settings"
     linking straight to the user's `app.graph8.com` Settings → Mailboxes
     page (new tab). Below it, poll `GET /mailboxes` via `Graph8Client.list_mailboxes()`
     and show a live "Connected ✅ / Not connected" status pulled from
     graph8 — this is the `mailbox_status` table from Section 5.
   - Once connected, replies land in graph8's own **AI Inbox** automatically
     — nothing else to build for ingestion.
3. **Getting that data into OUR dashboard in real time** is what
   `webhook_receiver` (Section 13) is for: register a graph8 webhook for
   inbox/reply events (`Graph8Client.register_webhook()`), and every new
   reply graph8 receives on the connected Gmail mailbox fires our
   `/webhooks/graph8` endpoint → writes to `events` → broadcasts over SSE
   → shows up live on the Inbox / Replies page (Section 11, page 5). This
   is the exact same webhook path Section 13 already describes — email
   ingestion doesn't need a separate system, it's the same feedback loop
   the rest of the app already runs on.
4. **If you still want an n8n layer for extra visual flair for judges**,
   build it as described in the corrected Section 15: n8n receives the
   *same* graph8 webhook (or polls `GET /inbox` on a Cron node) and relays
   it onward (e.g., posts a Slack notification, or forwards to our
   backend). n8n in this design never touches Gmail directly and never
   handles user credentials — it's a relay/automation layer sitting on top
   of graph8's already-connected mailbox, which is both safer and far less
   work than standing up n8n's own Gmail OAuth node per end-user.

This gives you the real-time "emails show up on the dashboard the moment
the user connects their inbox" experience you wanted, without building or
being responsible for a second OAuth system.

## 7. LLM CLIENT — PROVIDER-SWAPPABLE BY DESIGN

*(unchanged from your draft)*

Use Groq for MVP (fast, free tier, good for live demo latency). Build
`backend/app/llm/llm_client.py` using the OpenAI-compatible client
interface, because Groq's API is OpenAI-compatible.

```python
from openai import OpenAI
import os

class LLMClient:
    def __init__(self):
        self.client = OpenAI(
            base_url=os.environ.get("LLM_BASE_URL", "https://api.groq.com/openai/v1"),
            api_key=os.environ.get("LLM_API_KEY"),
        )
        self.model = os.environ.get("LLM_MODEL", "llama-3.3-70b-versatile")

    def generate(self, messages: list[dict], **kwargs) -> str:
        resp = self.client.chat.completions.create(
            model=self.model,
            messages=messages,
            **kwargs,
        )
        return resp.choices[0].message.content
```

To switch providers later: change `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`
in `.env` only. Never reference "groq" directly anywhere else in the
codebase — always go through `LLMClient`. (If the team ever wants native
Anthropic API instead of an OpenAI-compatible endpoint, that needs a small
adapter change since Anthropic's message schema differs slightly — flag in
a code comment, don't silently break it.)

## 8. LANGGRAPH WORKFLOW (the core loop)

*(unchanged from your draft — still correct)*

Build as a LangGraph `StateGraph` with a real cyclical edge (not a straight
DAG) — make it structurally visible in the code.

**Nodes:**
1. `signal_node` — pulls high-intent accounts from graph8 signals
   (`Graph8Client.list_intent_keywords` → `get_companies_for_keyword`) for
   the campaign's ICP filter.
2. `enrichment_node` — enriches each account/contact via
   `Graph8Client.search_contacts` / `enrich_person`.
3. `variant_generator_node` — generates 2 pitch variants (subject + body)
   per segment using `LLMClient`, using saved `reference_emails` as
   few-shot examples. Tag each variant with a generation reason.
4. `executor_node` — enrolls contacts into a graph8 sequence per variant
   via `Graph8Client.add_contacts_to_sequence`, splitting the segment
   evenly across active variants.
5. `feedback_node` — triggered by incoming webhook events (not polling).
   Updates `events`, recalculates each variant's live metrics.
6. `reallocation_node` — the reinforcement step. Require a minimum sample
   size (e.g. 5 sends) before any kill/reallocate decision. Every
   "kill_variant" or "generate_variant" decision writes an `approvals` row
   with `requires_approval=True` **before** it takes effect (Section 9).
7. `voice_escalation_node` — stretch goal, Section 10.

**State schema** (`state.py`): campaign_id, segment, contacts[], variants[],
events[], last_decision, pending_approvals[].

Use LangGraph checkpointing (Postgres checkpointer against Supabase) so
state persists across webhook-triggered re-entries at `feedback_node`.

## 9. HUMAN-IN-THE-LOOP GATES

*(unchanged from your draft — still correct)*

Gate behind an `approvals` row requiring explicit user approve/reject/edit:

  approval in this MVP).

see): pulling signals, enriching contacts, recalculating variant metrics,
generating the first two variants for a new campaign.
